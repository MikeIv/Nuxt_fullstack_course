# Цикл работы агента

Перед нетривиальной задачей — **класс** и **фаза**. Фазы не пропускать без согласия.

Класс определяет **агент**, не человек: для M+ он называется одной строкой в блоке «Понимание», чтобы человек мог поправить сразу. Если scope вырос — файлов или модулей больше, чем предполагалось, — переобъяви класс и переключись на процесс нового класса, а не продолжай молча.

| Класс  | Примеры           | Процесс                                     |
| ------ | ----------------- | ------------------------------------------- |
| **S**  | typo, rename      | Execute → Verify                            |
| **M**  | фича, 1–4 файла   | Discuss → Execute → Verify                  |
| **L**  | модуль, 5+ файлов | Discuss → Plan → Execute (волнами) → Verify |
| **XL** | миграция          | Полный цикл + `.planning/`                  |

**Фазы:** Discuss (`01`) → Plan (`02`, L+) → Execute (`03`) → Verify (`04`).

**Verify:** по `04` — S lint · M `pnpm lint:all` (+ `typecheck` при API) · L+ `pnpm verify` + `pnpm build`.

**Принципы:** минимальный diff · эталон из репо (`90`) · причина, не симптом (M+) · типы первыми (L+/API) · неуверенность → Discuss.

**Стоп:** противоречивые требования; auth/роли/контракт API; удаление данных; нет env/API; scope меняется — спросить.

**Язык:** русский. **Приоритет:** проектные правила > личные (Cursor User Rules / `~/.dsh/AGENTS.md`).

# Маршрутизация инструментов

Исполнителей двое, процесс один: правила действуют в обоих инструментах.
Инструмент — это **исполнитель волны**, а не «место, где я работаю».

## Роли

- **Писатель** — один инструмент на волну: правит код, запускает свои проверки, закрывает волну.
- **Проверяющий** — **другой** инструмент: сообщает только факты (расхождения с brief, упавшие проверки, нарушения правил). **Сам не правит.**
- **Решающий** — человек: brief, план, коммит. Класс задачи определяет агент (`00`), человек корректирует его одним словом.

Находки вносит автор волны; проверяющий только докладывает.

## Кто на какой работе

| Работа | Инструмент |
| --- | --- |
| Микроправки, визуальная подгонка, LSP-переименования, правка «на глаз» | Cursor |
| Волны L/XL: много файлов, прогоны, ожидания, повторы | DS Harness |
| Механическая верификация: линты, сверка `git diff` с brief, поиск нарушений правил | DS Harness |
| Содержательное ревью: архитектура, риски, спорные места | Cursor либо DS Harness на усиленной модели |

**Класс M:** пишет **Cursor**, проверяет **DS Harness** фактами по `git diff` и brief — по завершении задачи, а не после каждой правки.
**Класс L/XL:** план через DS Harness, волны по 1–3 задачи, проверка **другим** инструментом после каждой волны.
**Класс S:** только Cursor — правка и линт, без `.planning/` и без аудита.

Эвристика: **печатаешь и смотришь глазами — Cursor; ждёшь и проверяешь — DS Harness; решаешь — человек.**

**Ограничение песочницы.** DS Harness сам запускает линты и `git`. Всё, что поднимает `esbuild` — тест-раннер, `build`, `dev` — и сетевые вызовы (Figma REST, MCP) требуют расширения доступа: их запускает автор, а невыполненную проверку указывают в отчёте.

## Передача: шина — `.planning/`

- `brief.md` — вход задачи M+ (`brief-template.md`); `plan.md` — план L/XL.
- `state.md` — выход каждой волны; строки **«Ручка у»** и **«Файлы волны»** обязательны.
- **У файла в единицу времени один писатель.** Арбитр — `git status` / `git diff`.

## Запрещено

- Двум инструментам править одни файлы одновременно.
- `build` пока жив `dev` — они дерутся за `.nuxt`. Пока dev запущен, проверки идут линтами, а тесты запускает автор.
- Править `AGENTS.md` руками: он генерируется из `.cursor/rules` командой `node .cursor/sync-rules.mjs`.
- Коммитить без явной просьбы (`03`).
- Аудит в режиме записи: аудит ведётся в сессии с правами **read-only**.

## Словарь инструментов

Имена Cursor в правилах (`Task explore`, `ReadLints`, команды `/brief` и др.) переводятся в `AGENTS.local.md`, раздел «Инструменты Cursor → DS Harness».
